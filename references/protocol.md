# sshhh 状态协议

描述 `scripts/sshhh.py` 与调用方（AI agent）之间的约定。

## 输出通道

| 通道 | 内容 |
|------|------|
| stdout | 远端命令的标准输出；配置类命令的人类可读提示 |
| stderr | 错误信息；状态标记行 `SSHHH_STATUS: <NAME>` |
| 退出码 | 远端命令的退出码，或下列保留码 |

## 保留退出码

| 码 | 名称 | 含义 | 建议动作 |
|----|------|------|----------|
| 0 | — | 成功 | 使用输出 |
| 2 | — | **参数格式错误** | 修正调用方式 |
| 3 | — | **配置/状态错误** | 读 stderr |
| 4 | — | 网络或认证失败 | 读 stderr，必要时 `test` |
| 10 | `CONFIGURED` | 用户刚完成初始化配置 | 重试原命令（一次） |
| 11 | `CANCELLED` | 用户在配置窗口取消 | 停止重试，告知用户 |
| 12 | `TIMEOUT` | 窗口等待超时，或被宿主回收 | 告知用户手动执行 hint 中的命令 |
| 13 | `LOCKED` | 密码库无法自动解锁 | 告知用户执行 `unlock` |
| 14 | `HOST_ADDED` | 用户刚添加了目标主机 | 重试原命令（一次） |
| 15 | `SETUP_PENDING` | 配置窗口已打开，正在等用户输入 | 告知用户去窗口完成，不要重跑 |
| 20 | `NO_RUNTIME` | venv 或依赖未就绪 | 告知用户执行 `setup` |

### 2 与 3 的边界

这两个码容易混，按「错误发生在哪一层」区分：

- **2 = 调用方式不对**，参数缺失、顺序错误、命令为空。重发一次正确的调用即可解决。
  - `sshhh run`（没给主机）
  - `sshhh run prod`（没给命令）
  - `sshhh put prod a`（少一个路径参数）
  - `sshhh --bogus-flag run prod x`（未知选项被当成主机名时同样归此类）

- **3 = 调用方式没问题，但当前状态做不到**。需要先改变状态。
  - `sshhh test ghost-host`（参数正确，但这台机器不在清单里）
  - `sshhh put ghost-host a b`（同上）
  - `sshhh unlock`（还没初始化，没有密码库）
  - 配置文件损坏、内部异常

注意：`sshhh run ghost-host "ls"` **不返回 3**，而是弹窗添加主机 → 14 或 11。
只有 `test` / `put` / `get` / `setpass` 这类明确指定主机的命令才会返回 3。

## 状态行格式

```
SSHHH_STATUS: CONFIGURED
SSHHH_MESSAGE: 已经完成初始化配置，请重试这条命令
SSHHH_HINT: 配置完成，直接重试原命令即可。
```

三行都可能出现，`SSHHH_STATUS` 一定在第一行。行内不含任何凭据。

## 歧义处理

远端命令本身可能返回 10-14 或 20，与保留码冲突。区分方式：

- **有 stdout 输出** → 是远端命令的结果，退出码按远端含义解释
- **stdout 为空且 stderr 有 `SSHHH_STATUS`** → 是协议状态

## 配置窗口的行为

| 触发条件 | 窗口任务 | 用户看到 | 成功 | 取消 |
|----------|----------|----------|------|------|
| `~/.sshhh/vault.enc` 不存在 | `setup` | 设主密码 + 加第一台服务器 | 10 | 11 |
| 密码库存在但主密码取不到 | `unlock` | 只输入主密码 | 继续执行 | 11 |
| 主机不在清单里，或该主机缺密码 | `add_host` | 填地址、用户名、端口、密码 | 14 | 11 |

`setpass <主机>` 复用 `add_host` 任务，但带 `reset_password: true`：这时窗口
**只问新密码**，地址、端口、用户名不重问，`sudo` / `key_file` / 命令策略等
向导不问的字段原样保留。落盘前会重新读一次主机清单，以磁盘上的最新值为基底
合并本次输入，避免向导打开期间的并发修改被覆盖。

窗口本身：

- 是真正的控制台（`cmd.exe` 窗口），`getpass` 能正常隐藏输入
- **由系统资源管理器（explorer.exe）拉起**，不在调用方进程的进程树和作业对象里：
  脚本退出、agent 的命令超时被打断，都不会关掉窗口
- 同一个窗口工作目录只允许一个向导实例（`.claimed` 独占创建），重复拉起时
  后到的那次直接退出，不会出现两个向导抢同一个键盘
- 等待 **120 秒**（`SSHHH_SETUP_HANDOFF`）用户还没输完 → 返回 **15 `SETUP_PENDING`**，
  脚本正常退出，窗口继续留着给用户用
- **已经有一个窗口在运行时，新的调用立即返回 15**（详情带 `active: true`）：
  不再等 120 秒，也不会开第二个窗口。用户在配置期间 agent 反复调用不会造成
  重复弹窗，也不会误判成"配置失败"
- 用户按 `Ctrl+C` → 窗口退出 → 结果文件为 `cancel` → 返回 11
- 用户点窗口右上角 X → 结果文件缺失 → 同样按取消处理
- 等待超过 **180 秒**（`SSHHH_SETUP_TIMEOUT`）→ `taskkill /T /F` 结束窗口 → 返回 12

### 为什么窗口要交给 explorer 启动

宿主如果把每条命令放进作业对象（job object），命令结束就回收残留进程，
那么子进程窗口会被一起杀掉 —— 用户正输着主密码，窗口突然消失。

Windows 上 `CREATE_BREAKAWAY_FROM_JOB` 在多数作业对象里不起作用。实测唯一可靠
的做法是把启动动作交给 explorer.exe：窗口归属 explorer，不在作业对象里，
命令结束后依旧存活。

代价是拿不到 `Popen` 句柄，所以改成：窗口自己在 `pid.json` 里写 PID，
父进程轮询结果文件 + 检查该 PID 是否存活。

### 交接（SETUP_PENDING）是为什么

不是为了保住窗口（窗口已经独立了），而是让 agent **早点拿到明确状态**：
用户填完主密码还要填服务器地址、用户名、端口、密码，一两分钟很正常，
让 agent 的命令一直挂着没有意义。交接后 agent 可以告诉用户「去窗口里填」，
用户在窗口里操作，完成后再重试。

### 宿主回收窗口的识别与降级

交接出去的下一次调用会检查：那个窗口还在吗？配置完成了吗？

- 窗口还活着 → 继续等 25 秒，仍是 15
- 窗口没了、配置也没完成，且**交接后 15 秒内**就消失 → 判定为宿主回收，
  写入标记文件 `~/.sshhh/.no-window`，本次返回 **12**，hint 指向 `config --here`
- 窗口没了，但过了很久才消失 → 判定为用户主动关窗，按 11 取消处理

`~/.sshhh/.no-window` 存在期间，脚本不再尝试弹窗，`SSHHH_HINT` 里的
`config` 会自动写成 `config --here`（在当前终端里配置，没有子进程可被杀）。
用户配完之后这个标记自动失效，因为 `vault.enc` 已经存在，不再需要窗口。

### 超时参数

`SSHHH_SETUP_TIMEOUT` 单位为秒，**默认 180，合法范围 30–600**。
超出范围、非数字、负数一律回落默认值 180，不会报错也不会无限等待。

注意：这个环境变量只影响**配置窗口**的等待时长，不影响并发锁的 30 秒上限。

### 与 agent 命令超时的关系

三层超时由内向外递增，保证内层总能先超时并返回状态码，外层还来得及处理：

```
pip 安装 150s  <  窗口交接 120s  <  建议首次调用 300s
```

- agent 的命令超时若 **< 150s**：pip 卡在网络上时 agent 会先被打断，
  用户看到的是「命令超时」而不是「安装依赖超时」，脚本里写好的提示永远发不出来
- 窗口只等 120 秒就交接，所以 agent 不必为窗口留 180 秒；
  最坏情况是「装依赖 150s + 交接 120s」，300s 足够
- 即使 agent 的命令中途被杀，窗口也不受影响（它不在作业对象里），
  用户输完就生效，下次调用直接可用

日常调用（环境已就绪、密码库已解锁）1-2 秒返回，给 60 秒足够。

### NO_RUNTIME 的两种成因

| 成因 | 脚本能否自己发现 | hint 指向 |
|------|------------------|-----------|
| Python 版本低于 3.9 | 能 | 升级 Python |
| 依赖下载失败 / 超时 | 能 | 跑 `setup`，必要时换 `PIP_INDEX_URL` |
| **机器完全没装 Python** | **不能** | 脚本根本启动不了，由 agent 看到 `command not found` 后自行判断 |

最后一行是协议边界：脚本只能检测到「有 Python 但太旧」，检测不到「没有 Python」。
这种情况不会出现任何状态码，agent 需要根据 shell 报错自行引导用户。

## 并发与锁

多个 agent 可能同时触发配置（例如两个窗口同时收到「连一下服务器」）。

- `vault.enc` / `hosts.toml` 的所有写入都在 `~/.sshhh/.lock` 文件锁保护下串行执行
- 锁是非阻塞获取 + 重试，**单个写操作最多等待 30 秒**
- 超过 30 秒仍未拿到锁 → 返回 **3**（不是 12），stderr 提示
  「另一个 sshhh 进程正在配置，请稍后重试」
- 后到的 agent 会看到自己的调用短暂停顿（通常 < 1 秒），这是正常现象，
  不是卡死；只有持续超过 30 秒才需要提示用户
- 加锁范围只包含「读-改-写」这一小段，配置窗口等待用户输入的整个过程
  **不持有锁**，所以不会阻塞其他 agent 的只读操作（`list` / `run`）

### 四个超时不要混

协议里有四个独立的超时 / 等待时长，量级相近但含义完全不同：

| 项目 | 上限 | 到点行为 | 能否调整 |
|------|------|----------|----------|
| 并发锁等待 | 30 秒（固定） | 返回 **3**，提示另一个进程正在配置 | 不能 |
| pip 安装依赖 | 150 秒（固定） | 返回 **20**，提示「安装依赖超时，网络可能不通」 | 不能 |
| 窗口交接 | 120 秒（默认） | 返回 **15**，脚本正常退出，窗口留给用户 | 能，`SSHHH_SETUP_HANDOFF`，0 = 不交接 |
| 硬超时杀窗口 | 180 秒（默认） | 返回 **12**，`taskkill` 结束窗口 | 能，`SSHHH_SETUP_TIMEOUT` 30–600 |

一句话区分：

- 看到 **3** 且提到「另一个进程正在配置」→ 锁没抢到，稍后重试
- 看到 **20** 且提到超时/pip → 网络问题，让用户换源后跑 `setup`
- 看到 **15** → 窗口还开着，让用户去里面填，别重跑
- 看到 **12** → 窗口已经不在了（超时被杀或被宿主回收），让用户手动跑 hint 里的命令

## 回传文件的实现约束

配置窗口的结果通过一个临时 JSON 文件回传给父进程，父进程读完即删。

**该文件只允许出现三个字段：**

```json
{"status": "ok | cancel | error", "host": "主机名", "error": "错误摘要"}
```

硬约束（代码强制，不只是文档约定）：

- 写侧 `console_setup._write_result()` 用 `RESULT_KEYS` 白名单过滤，
  不在白名单的 key 一律丢弃
- 读侧 `console._read_result()` 用同一份白名单二次过滤，
  即使文件被人为改动也不会把多余字段带进来
- `status` 不合法时整体判为 `error`

也就是说，密码、主密码、密钥材料**在任何情况下都不会经由这个文件流转**。
修改这里时请同步更新两处白名单。

## 密码的流转

```
用户输入 (窗口进程内存)
        │
        ├─→ AES-GCM 加密 ─→ ~/.sshhh/vault.enc
        └─→ 主密码 ────────→ Windows 凭据管理器
                              │
agent 调用时 ─────────────────┘
        │
        └─→ 脚本取出明文 → paramiko.connect() → 用完即弃
```

明文不落盘、不进 argv、不进环境变量、不进日志、不回显。

## 数据目录

固定为 `~/.sshhh/`，与 skill 的安装位置无关。装多份 skill 副本也共用这一份数据。

| 文件 | 内容 |
|------|------|
| `vault.enc` | AES-GCM 加密的密码库 |
| `hosts.toml` | 主机清单，**无密码字段** |
| `audit.log` | JSONL 审计日志，命令写入前已脱敏 |
| `known_hosts` | TOFU 记录的主机指纹 |
| `console.log` | 配置窗口的诊断日志（流程与异常，不含任何用户输入） |
| `.lock` | 跨进程文件锁 |
| `.setup-*/` | 进行中的配置窗口工作目录：`run.cmd` / `payload.json` / `pid.json` / `stderr.log` |
| `.pending` | 上一次交接出去的窗口（用于识别它是否被外部关掉） |
| `.no-window` | 该环境弹窗撑不住的标记，存在时改用 `config --here` |
| `venv/` | 共享运行时（首次调用时创建，约 35 MB） |

环境变量 `SSHHH_DATA_DIR` 可覆盖此目录，**仅供测试隔离使用**。

## 策略与审计的覆盖范围

策略（`[hosts.<名称>.policy]`）分两组，互不代替：

| 字段 | 管什么 | 匹配对象 |
|------|--------|----------|
| `allow` / `deny` | `run` | 整条命令（`fullmatch`） |
| `allow_put` / `deny_put` | `put` | 远端目标路径（前缀匹配） |
| `allow_get` / `deny_get` | `get` | 远端源路径（前缀匹配） |

- 命令规则用 `fullmatch`：`^df -h$` 只放行 `df -h`，放过不 `x; df -h`。
  要拦一族命令写 `^rm -rf.*`，只写 `^rm -rf` 只拦「正好等于」那一条。
- 命令含 shell 元字符（`;` `&` `|` `$` 反引号 `>` `<` 换行）时**默认拒绝**，
  除非该主机段里写了 `allow_shell = true`。
- 白名单非空时不匹配即拒绝；`deny` 优先。
- 配了 `allow` 命令白名单的主机，文件通道默认关闭（需显式 `allow_put` / `allow_get`）。
- 拒绝发生在连接之前：不建连、退出码 1、写 `run.denied` / `transfer.denied`。

**定性**：本地策略是**防手滑，非安全边界**。`hosts.toml` 与 `scripts/` 对同用户
进程可写，绕过它不需要任何技巧（改文件或直接调 `lib.transport`）；它的价值是
给误操作加摩擦、给拒绝留记录。唯一 agent 绕不过的强制在服务端（受限
`authorized_keys` + 服务端包装），不在本档实现范围内。

审计（`audit.log`）覆盖所有触达凭据或远端的动作，`action` 取值：

`run`、`run.denied`、`transfer.put`、`transfer.get`、`transfer.denied`、
`test`、`setpass`、`unlock`、`migrate`、`vault.open`。

`vault.open` 记录的是「谁解密了密码库」：pid、解释器、工作目录、命令行**前两个
参数**。它拦不住同用户进程直接调用 `lib.vault`（操作系统级边界），但能让这条路
留痕。

只留前两个参数是刻意的：整串 `sys.argv` 会把调用方顺手写在命令里的秘密一起
落盘（`run prod --stdin S3cret mysql -pS3cret` 就是原样两条），而 redactor 只认得
主密码和库里已有的值。落盘前仍会再过一遍 redactor，作第二道保险。

同理，标准输入的内容只能来自管道（`--stdin -`）或 `--stdin-file <文件>`，
**不接受 `--stdin <值>`** —— 值会进 argv、进程列表和审计，所以这种写法现在
直接报参数错误（退出码 2），而不是默默放行。审计记录里也不再有 `caller`
字段：它取自定义方随便就能设置的环境变量，只是「有归属」的错觉。
