# sshhh 状态协议

描述 `scripts/sshhh.py` 与调用方（AI agent）之间的约定。

## 输出通道

| 通道 | 内容 |
|------|------|
| stdout | 远端命令的标准输出；配置类命令的人类可读提示 |
| stderr | 错误信息；状态标记行 `SSHHH_STATUS: <NAME>` |
| 退出码 | 远端命令的退出码，或下列保留码 |

## 输出截断

`run` 的 stdout / stderr 各有 **50 KiB** 默认上限（`lib.output.DEFAULT_MAX_BYTES`），
超过时保留开头 60% 与结尾 40%，中间插入一行提示：

```
[sshhh] 输出已截断（原始 N 字节，只保留开头约 A 与结尾约 B 字节）；需要完整内容请缩小命令范围，或用 --max-bytes / --tail 调整
```

- `--tail N`：只回传最后 N 行，**优先于** `--max-bytes`。行数不足 N 时不插提示
- `--max-bytes N`：改上限；`0` 表示不限制；负数或非整数 → 退出码 2
- 截断只影响回传给调用方的内容：审计记录里带 `truncated: true` 与 `bytes`（原始字节数），
  事后可以区分「命令只产出了这么多」和「我们只回了这么多」
- 读取侧另有独立硬顶（#40）：每条流读够 `--max-bytes` × 4 就停止接收，stderr 提示
  「超过单次读取上限」—— 这是内存封顶（TM-A4 的读取侧），与回传截断相互独立；
  `--max-bytes 0` 时两侧都不限
- `--timeout N` 是墙钟上限（#40）：单次 recv 超时不触发「远端持续产出」的场景，
  所以 deadline 按 drain 每拿到一块数据检查一次；到点先关通道再收线程，命令必返回。
  远端不发退出状态时同样按 deadline 中止，客户端不可能挂死
- 提示行本身是给调用方看的信号：看到它说明拿到的不是全部输出，应缩小命令范围，
  而不是把结论建立在残缺输出上
- 远端退出码照常透传，截断不改变退出码

## 保留退出码

| 码 | 名称 | 含义 | 建议动作 |
|----|------|------|----------|
| 0 | — | 成功 | 使用输出 |
| 2 | — | **参数格式错误** | 修正调用方式 |
| 3 | — | **配置/状态错误** | 读 stderr |
| 4 | — | 网络或认证失败 | 读 stderr，必要时 `test` |
| 10 | `CONFIGURED` | 用户刚完成初始化配置 | 重试原命令（一次） |
| 11 | `CANCELLED` | 用户在配置窗口取消 | 停止重试，告知用户 |
| 12 | `TIMEOUT` | 窗口等待超时、被宿主回收，或本环境无弹窗条件（非 Windows / 非 tty / `.no-window`） | 照抄 hint：让用户在自己的终端里执行 |
| 13 | `LOCKED` | 密码库无法自动解锁 | 告知用户执行 `unlock` |
| 14 | `HOST_ADDED` | 用户刚添加了目标主机 | 重试原命令（一次） |
| 15 | `SETUP_PENDING` | 配置窗口已打开，正在等用户输入 | 告知用户去窗口完成，不要重跑 |
| 20 | `NO_RUNTIME` | venv 或依赖未就绪 | 告知用户执行 `setup` |

### 2 与 3 的边界

这两个码容易混，按「错误发生在哪一层」区分：

- **2 = 调用方式不对**，参数缺失、顺序错误、命令为空。重发一次正确的调用即可解决。
  - `sshhh run`（没给主机）
  - `sshhh run prod`（没给命令）
  - `sshhh put prod a`（少一个路径参数）
  - `sshhh --bogus-flag run prod x`（未知选项被当成主机名时同样归此类）

- **3 = 调用方式没问题，但当前状态做不到**。需要先改变状态。
  - `sshhh test ghost-host`（参数正确，但这台机器不在清单里）
  - `sshhh put ghost-host a b`（同上）
  - `sshhh unlock`（还没初始化，没有密码库）
  - 配置文件损坏、内部异常

注意：`sshhh run ghost-host "ls"` **不返回 3**，而是弹窗添加主机 → 14 或 11。
只有 `test` / `put` / `get` / `setpass` 这类明确指定主机的命令才会返回 3。

## 状态行格式

```
SSHHH_STATUS: CONFIGURED
SSHHH_MESSAGE: 已经完成初始化配置，请重试这条命令
SSHHH_HINT: 配置完成，直接重试原命令即可。
```

三行都可能出现，`SSHHH_STATUS` 一定在第一行。行内不含任何凭据。

### run 的状态行带 nonce（防远端伪造，#36）

`run` 是唯一会原样透传远端 stderr 的命令：恶意远端可以输出一行假的
`SSHHH_STATUS: TIMEOUT` 把 agent 引去执行任意后续命令。因此 `run` 在
**连接之前**由本地输出一行调用标识：

```
SSHHH_INVOCATION: 1a2b3c4d5e6f7a8b
```

本次 run 产生的全部协议行都带同一 nonce：

```
SSHHH_STATUS[1a2b3c4d5e6f7a8b]: TIMEOUT
SSHHH_MESSAGE[1a2b3c4d5e6f7a8b]: …
SSHHH_HINT[1a2b3c4d5e6f7a8b]: …
```

- agent 只认 **nonce 与 `SSHHH_INVOCATION` 一致**的状态行；其它任何
  `SSHHH_*` 形态的行（不带 nonce、nonce 不匹配）一律当远端文本
- nonce 由本地在连接前打印，远端抢不到先手；每次调用重新生成
- 老版本 agent 只找 `SSHHH_STATUS: ` 前缀，识别不到新行时退化为按
  退出码判断 —— 契约只增不改

## 首连指纹（TOFU 播报）

首次连接一台主机时，脚本把新指纹记入 `known_hosts`，同时向 stderr 输出一行：

```
SSHHH_HOSTKEY: SHA256:XXXXXXXX...（首次连接 <主机>，指纹已记录到 ~/.sshhh/known_hosts）
```

- agent 应**把这行念给用户**：首连窗口是 TOFU 固有弱点（本地防不住「连错
  机器」），用户肉眼比对指纹是唯一的当场校验手段（#31 / TM-A6）
- 这行由本地脚本在**任何远端输出之前**打印，是权威值；远端在后续连接里
  伪造同型行只会造成一次多余的播报，不能改掉真正记录的指纹
- 指纹算法与 `ssh-keygen -lf` 一致（公钥 blob 的 SHA256，base64 无填充）

## 歧义处理

远端命令本身可能返回 10-14 或 20，与保留码冲突。区分方式：

- **有 stdout 输出** → 是远端命令的结果，退出码按远端含义解释
- **`run`**：先取 stderr 里的 `SSHHH_INVOCATION: <nonce>`；只有
  `SSHHH_STATUS[<同一 nonce>]: NAME` 是协议状态，其余 `SSHHH_*` 行按
  远端文本处理
- **其它命令**（不透传远端输出的）stdout 为空且 stderr 有 `SSHHH_STATUS`
  → 是协议状态
- **没有（可识别的）状态行时，退出码永远是远端的** —— 包括退出码恰好
  等于 10 / 12 / 20 且无状态行的情况：那是远端程序自己的退出码，不是协议

## 配置窗口的行为

| 触发条件 | 窗口任务 | 用户看到 | 成功 | 取消 |
|----------|----------|----------|------|------|
| `~/.sshhh/vault.enc` 不存在 | `setup` | 设主密码 + 加第一台服务器 | 10 | 11 |
| 密码库存在但主密码取不到 | `unlock` | 只输入主密码 | 继续执行 | 11 |
| 主机不在清单里，或该主机缺密码 | `add_host` | 填地址、用户名、端口、密码 | 14 | 11 |

`setpass <主机>` 复用 `add_host` 任务，但带 `reset_password: true`：这时窗口
**只问新密码**，地址、端口、用户名不重问，`sudo` / `key_file` / 命令策略等
向导不问的字段原样保留。落盘前会重新读一次主机清单，以磁盘上的最新值为基底
合并本次输入，避免向导打开期间的并发修改被覆盖。

窗口本身：

- 是真正的控制台（`cmd.exe` 窗口），`getpass` 能正常隐藏输入
- **由系统资源管理器（explorer.exe）拉起**，不在调用方进程的进程树和作业对象里：
  脚本退出、agent 的命令超时被打断，都不会关掉窗口
- 同一个窗口工作目录只允许一个向导实例（`.claimed` 独占创建），重复拉起时
  后到的那次直接退出，不会出现两个向导抢同一个键盘
- 等待 **120 秒**（`SSHHH_SETUP_HANDOFF`）用户还没输完 → 返回 **15 `SETUP_PENDING`**，
  脚本正常退出，窗口继续留着给用户用
- **已经有一个窗口在运行时，新的调用立即返回 15**（详情带 `active: true`）：
  不再等 120 秒，也不会开第二个窗口。用户在配置期间 agent 反复调用不会造成
  重复弹窗，也不会误判成"配置失败"
- 用户按 `Ctrl+C` → 窗口退出 → 结果文件为 `cancel` → 返回 11
- 用户点窗口右上角 X → 结果文件缺失 → 同样按取消处理
- 等待超过 **180 秒**（`SSHHH_SETUP_TIMEOUT`）→ `taskkill /T /F` 结束窗口 → 返回 12

### 为什么窗口要交给 explorer 启动

宿主如果把每条命令放进作业对象（job object），命令结束就回收残留进程，
那么子进程窗口会被一起杀掉 —— 用户正输着主密码，窗口突然消失。

Windows 上 `CREATE_BREAKAWAY_FROM_JOB` 在多数作业对象里不起作用。实测唯一可靠
的做法是把启动动作交给 explorer.exe：窗口归属 explorer，不在作业对象里，
命令结束后依旧存活。

代价是拿不到 `Popen` 句柄，所以改成：窗口自己在 `pid.json` 里写 PID，
父进程轮询结果文件 + 检查该 PID 是否存活。

### 交接（SETUP_PENDING）是为什么

不是为了保住窗口（窗口已经独立了），而是让 agent **早点拿到明确状态**：
用户填完主密码还要填服务器地址、用户名、端口、密码，一两分钟很正常，
让 agent 的命令一直挂着没有意义。交接后 agent 可以告诉用户「去窗口里填」，
用户在窗口里操作，完成后再重试。

### Windows 弹窗链路：保留决策与测试盲区（#23）

数据评估（2026-11-15，console.log）：真实使用中弹窗 2 次（首跑 `setup`、
`add_host`），**全部成功**，没有一次落到 `config --here` 降级。按 #23 的
决策规则（依据数据），链路**保留**。

代价与盲区（如实标注）：

- 约 700 行 Windows 专属编排（launcher / console 的 nt 分支 / console_setup
  的 CONIN$、msvcrt 键盘读取、`.claimed` 独占、交接回收启发式）
- 自动化测试覆盖的是编排语义（MockConsole 的状态流转、结果文件白名单、
  pid 存活判定）；**真实 explorer 拉起、真实 cmd 窗口的键盘输入、taskkill
  回收、交接后 15 秒启发式**只能人工验证
- 上述模块的 docstring 已标注盲区；非 Windows 退化为 `_launch_inline`
  （当前终端跑向导），有 #33 的针对性文案兜底

### 宿主回收窗口的识别与降级

交接出去的下一次调用会检查：那个窗口还在吗？配置完成了吗？

- 窗口还活着 → 继续等 25 秒，仍是 15
- 窗口没了、配置也没完成，且**交接后 15 秒内**就消失 → 判定为宿主回收，
  写入标记文件 `~/.sshhh/.no-window`，本次返回 **12**，hint 指向 `config --here`
- 窗口没了，但过了很久才消失 → 判定为用户主动关窗，按 11 取消处理

`~/.sshhh/.no-window` 存在期间，脚本不再尝试弹窗，`SSHHH_HINT` 里的
`config` 会自动写成 `config --here`（在当前终端里配置，没有子进程可被杀）。
用户配完之后这个标记自动失效，因为 `vault.enc` 已经存在，不再需要窗口。

### 超时参数

`SSHHH_SETUP_TIMEOUT` 单位为秒，**默认 180，合法范围 30–600**。
超出范围、非数字、负数一律回落默认值 180，不会报错也不会无限等待。

注意：这个环境变量只影响**配置窗口**的等待时长，不影响并发锁的 30 秒上限。

### 与 agent 命令超时的关系

三层超时由内向外递增，保证内层总能先超时并返回状态码，外层还来得及处理：

```
pip 安装 150s + 窗口交接 120s ≈ 270s  <  建议首次调用 300s
```

（两条内层超时不会同时发生：装依赖发生在首跑，交接发生在弹配置窗口时；
270s 是「最坏情况两者相加」的量级估算，不是精确上界。）

- agent 的命令超时若 **< 150s**：pip 卡在网络上时 agent 会先被打断，
  用户看到的是「命令超时」而不是「安装依赖超时」，脚本里写好的提示永远发不出来
- 窗口只等 120 秒就交接，所以 agent 不必为窗口留 180 秒；
  最坏情况是「装依赖 150s + 交接 120s」，300s 足够
- 即使 agent 的命令中途被杀，窗口也不受影响（它不在作业对象里），
  用户输完就生效，下次调用直接可用

日常调用（环境已就绪、密码库已解锁）1-2 秒返回，给 60 秒足够。

### NO_RUNTIME 的两种成因

| 成因 | 脚本能否自己发现 | hint 指向 |
|------|------------------|-----------|
| Python 版本低于 3.9 | 能 | 升级 Python |
| 依赖下载失败 / 超时 | 能 | 跑 `setup`，必要时换 `PIP_INDEX_URL` |
| 另一个进程正在首次准备环境（自举锁超时） | 能 | 等它结束再重试，别自己删 venv |
| **机器完全没装 Python** | **不能** | 脚本根本启动不了，由 agent 看到 `command not found` 后自行判断 |

最后一行是协议边界：脚本只能检测到「有 Python 但太旧」，检测不到「没有 Python」。
这种情况不会出现任何状态码，agent 需要根据 shell 报错自行引导用户。

## 并发与锁

多个 agent 可能同时触发配置（例如两个窗口同时收到「连一下服务器」）。

- `vault.enc` / `hosts.toml` 的所有写入都在 `~/.sshhh/.lock` 文件锁保护下串行执行
- 首次运行时另有一把**自举锁** `~/.sshhh/.bootstrap`：`venv` 的「检查 → 创建 →
  装依赖」全程串行。两个 agent 同时首跑时，后到的那个等前一个装完再复查，
  直接复用，不会两份进程同时 `rmtree` + `pip install` 互相破坏环境（#10）。
  它和 `.lock` 是两把锁：装依赖要几分钟，不能把期间的读写操作一起堵住
- 自举锁最多等 **300 秒**，等不到返回 **20 `NO_RUNTIME`**（不是 3），
  提示语说明「另一个进程正在首次准备运行环境」，让调用方稍后重试
- 锁**下沉在写函数内部**（`store.upsert_host` / `remove_host` / `set_policy`），
  调用方不需要记得加锁，新增调用点也不会漏；`migrate` 的整段迁移（新密码库 +
  主机 + 策略）在同一把锁里完成，不会留下迁移到一半的状态
- 锁**可重入**（同一线程）：外层已经持锁时，内层 `with data_lock()` 直接放行，
  不会自己等自己。按线程算，不按进程 —— 别在线程池里写数据目录
- 所有落盘都是 tmp + `os.replace` 原子替换：并发读要么读到旧内容、要么读到新内容，
  不会读到截断的 TOML（旧实现直接 `write_text`，窗口期内读到半截就报
  「hosts.toml 解析失败」）
- Windows 上原子替换的一瞬间，读侧 `open()` 可能拿到瞬时共享冲突（PermissionError），
  读取因此带了几次短重试，不会把这种情况当成「文件损坏」
- 锁是非阻塞获取 + 重试，**单个写操作最多等待 30 秒**
- 超过 30 秒仍未拿到锁 → 返回 **3**（不是 12），stderr 提示
  「另一个 sshhh 进程正在配置，请稍后重试」
- 后到的 agent 会看到自己的调用短暂停顿（通常 < 1 秒），这是正常现象，
  不是卡死；只有持续超过 30 秒才需要提示用户
- 加锁范围只包含「读-改-写」这一小段，配置窗口等待用户输入的整个过程
  **不持有锁**，所以不会阻塞其他 agent 的只读操作（`list` / `run`）

### 五个超时不要混

协议里有五个独立的超时 / 等待时长，量级相近但含义完全不同：

| 项目 | 上限 | 到点行为 | 能否调整 |
|------|------|----------|----------|
| 并发锁等待（`.lock`） | 30 秒（固定） | 返回 **3**，提示另一个进程正在配置 | 不能 |
| 自举锁等待（`.bootstrap`） | 300 秒（固定） | 返回 **20**，提示另一个进程正在首次准备运行环境 | 不能 |
| pip 安装依赖 | 150 秒（固定） | 返回 **20**，提示「安装依赖超时，网络可能不通」 | 不能 |
| 窗口交接 | 120 秒（默认） | 返回 **15**，脚本正常退出，窗口留给用户 | 能，`SSHHH_SETUP_HANDOFF`，0 = 不交接 |
| 硬超时杀窗口 | 180 秒（默认） | 返回 **12**，`taskkill` 结束窗口 | 能，`SSHHH_SETUP_TIMEOUT` 30–600 |

一句话区分：

- 看到 **3** 且提到「另一个进程正在配置」→ 锁没抢到，稍后重试
- 看到 **20** 且提到「首次准备运行环境」→ 另一个 agent 正在装环境，等它结束再试
- 看到 **20** 且提到超时/pip → 网络问题，让用户换源后跑 `setup`
- 看到 **15** → 窗口还开着，让用户去里面填，别重跑
- 看到 **12** → 窗口已经不在了（超时被杀或被宿主回收），让用户手动跑 hint 里的命令

## 回传文件的实现约束

配置窗口的结果通过一个临时 JSON 文件回传给父进程，父进程读完即删。

**该文件只允许出现三个字段：**

```json
{"status": "ok | cancel | error", "host": "主机名", "error": "错误摘要"}
```

硬约束（代码强制，不只是文档约定）：

- 写侧 `console_setup._write_result()` 用 `RESULT_KEYS` 白名单过滤，
  不在白名单的 key 一律丢弃
- 读侧 `console._read_result()` 用同一份白名单二次过滤，
  即使文件被人为改动也不会把多余字段带进来
- `status` 不合法时整体判为 `error`

也就是说，密码、主密码、密钥材料**在任何情况下都不会经由这个文件流转**。
修改这里时请同步更新两处白名单。

## 密码的流转

```
用户输入 (窗口进程内存)
        │
        ├─→ AES-GCM 加密 ─→ ~/.sshhh/vault.enc
        └─→ 主密码 ────────→ 系统凭据库（Windows 凭据管理器 / macOS 钥匙串 /
                              Linux Secret Service）
                              └─ 不可用时 → ~/.sshhh/master.gpg
                                 （gpg 加密文件，headless Linux 的
                                  一等公民后端，#19）
agent 调用时 ─────────────────┘
        │
        └─→ 脚本取出明文（钥匙串 → gpg 后端依次尝试）
            → paramiko.connect() → 用完即弃
```

headless 环境没有 Secret Service：主密码改用本机 gpg 私钥加密保存
（与 pass 同一套机制），不进 `SSHHH_MASTER` 这类 agent 可读的环境变量。
`master.gpg` 只在钥匙串不可用或未命中时被尝试，每次经它解锁同样写
`vault.open` 审计。

明文不落盘、不进 argv、不进环境变量、不进日志、不回显。

## 数据目录

固定为 `~/.sshhh/`，与 skill 的安装位置无关。装多份 skill 副本也共用这一份数据。

| 文件 | 内容 |
|------|------|
| `vault.enc` | AES-GCM 加密的密码库（含 `key:<host>` 私钥条目，同为密文） |
| `hosts.toml` | 主机清单，**无密码字段**，带完整性签名（#18） |
| `audit.log` | JSONL 审计日志，命令写入前已脱敏 |
| `known_hosts` | TOFU 记录的主机指纹 |
| `console.log` | 配置窗口的诊断日志（流程与异常，不含任何用户输入） |
| `.lock` | 跨进程文件锁 |
| `.setup-*/` | 进行中的配置窗口工作目录：`run.cmd` / `payload.json` / `pid.json` / `stderr.log` |
| `.pending` | 上一次交接出去的窗口（用于识别它是否被外部关掉） |
| `.no-window` | 该环境弹窗撑不住的标记，存在时改用 `config --here` |
| `tmp/` | `get` 允许落盘的临时目录：数据目录内唯一的可写位置 |
| `venv/` | 共享运行时（首次调用时创建，约 35 MB） |

环境变量 `SSHHH_DATA_DIR` 可覆盖此目录，**仅供测试隔离使用**。

## 策略与审计的覆盖范围

策略（`[hosts.<名称>.policy]`）分两组，互不代替：

| 字段 | 管什么 | 匹配对象 |
|------|--------|----------|
| `allow` / `deny` | `run` | 整条命令（`fullmatch`） |
| `allow_put` / `deny_put` | `put` | 远端目标路径（前缀匹配） |
| `allow_get` / `deny_get` | `get` | 远端源路径（前缀匹配） |

- 命令规则用 `fullmatch`：`^df -h$` 只放行 `df -h`，放过不 `x; df -h`。
  要拦一族命令写 `^rm -rf.*`，只写 `^rm -rf` 只拦「正好等于」那一条。
- 命令含 shell 元字符（`;` `&` `|` `$` 反引号 `>` `<` 换行）时**默认拒绝**，
  除非该主机段里写了 `allow_shell = true`。
- 白名单非空时不匹配即拒绝；`deny` 优先。
- 配了 `allow` 命令白名单的主机，文件通道默认关闭（需显式 `allow_put` / `allow_get`）。
- 拒绝发生在连接之前：不建连、退出码 1、写 `run.denied` / `transfer.denied`。

**定性**：本地策略是**防手滑，非安全边界**。`hosts.toml` 与 `scripts/` 对同用户
进程可写，绕过它不需要任何技巧（改文件或直接调 `lib.transport`）；它的价值是
给误操作加摩擦、给拒绝留记录。唯一 agent 绕不过的强制在服务端（受限
`authorized_keys` + 服务端包装），不在本档实现范围内。

## 文件通道的本地约束

远端路径由策略管，本地路径由下面这张表管。两边都在建连之前判断，
`realpath` 归一后再比较，符号链接与 `..` 绕不过去。

| 方向 | 本地路径要求 | 越界后果 |
|------|--------------|----------|
| `get` | 当前目录或其子目录，或 `~/.sshhh/tmp/`；不得落在 `~/.sshhh/`（`tmp/` 除外） | 退出码 1 + `transfer.denied` |
| `put` | 不在 `~/.sshhh/` 内，且是存在的普通文件 | 退出码 1 + `transfer.denied` |

为什么禁止写数据目录：`get prod /etc/shadow ~/.sshhh/hosts.toml` 可以把主机清单、
指纹库、密码库覆盖成远端内容（DoS，甚至改变后续连接的信任基础）；`put` 反过来
能把 `vault.enc` 整份送到远端。

传输本身有两条上限（`Settings.transfer_max_bytes` / `transfer_timeout`，
默认 64 MiB / 300 秒），都可用 `--max-bytes` / `--timeout` 单次放宽：

- 超限一律报 **TransportError → 退出码 4**，提示里给出放宽命令，不静默截断
- 边收边算字节数：`stat` 报的大小不可信（文件在长、或者是特殊文件）
- 中途失败会删掉半截文件（本地目标 / 远端目标），避免「看起来传完了」
- SFTP 通道同时套上传超时，对端不发数据不会挂到 agent 超时为止

审计（`audit.log`）覆盖所有触达凭据或远端的动作，`action` 取值：

`run`、`run.denied`、`transfer.put`、`transfer.get`、`transfer.denied`、
`test`、`test.denied`、`setpass`、`unlock`、`migrate`、`vault.open`、
`reseal`、`key.gen`、`key.import`。

`vault.open` 记录的是「谁解密了密码库」：pid、解释器、工作目录、命令行**前两个
参数**。它拦不住同用户进程直接调用 `lib.vault`（操作系统级边界），但能让这条路
留痕。展示层分流（#26）：文件全保真；`audit` 命令默认隐藏 `vault.open`，
`--all` 看全量 —— 被诱导直接解密的行为在默认视图里看不到，但留痕始终在。

审计日志超过 10 MiB 自动轮转为 `audit.log.1`（只保留一代），`tail` 从文件
尾部倒读，不因日志增长而变慢。

触达远端的业务记录（`run` / `transfer.*` / `test` / `harden.check`）带
`auth` 字段标记本次认证方式：`key`（vault 密钥）或 `password`（#3 基线；
`key-file` 是 #18 之前的历史值，不再产生）。连接类记录另有
`fallback: "key"`（#3）：**密钥认证被服务器拒绝、本次连接回落到了密码**
—— 这是「服务器上的公钥被人拿掉 / 加固被静默移除」的唯一信号，stderr
同时有一行人读提示。被策略拒绝的记录（发生在连接之前）写的是「预期的主
认证方式」，没有 fallback 字段。

## hosts.toml 的完整性签名（#18）

hosts.toml 对 agent 可写，「删掉 `[hosts.x.policy]` 段就永久豁免策略」是
TM-B3 的攻击路径。清单因此带 HMAC-SHA256 签名（`[sshhh_integrity]` 段），
密钥从主密码派生 —— 修改清单从「编辑一个文本文件」升级为「解开密码库 +
import 内部模块」，落在 README 已声明的残余风险线上（同 UID 进程仍拦不住，
定性依旧是防手滑）。

- 签名对象是「去掉该段后、用 tomli-w 重新序列化」的规范形式：
  **注释与排版不参与签名**（手编注释不破坏签名），任何字段值改动都会失配
- run / test / put / get / harden 全部先验签，失败在建连前拒绝
  （退出码 3）并报错说明 —— 报错文案写明：手编后这是预期行为，先检查
  内容再 `sshhh manage reseal`；没改过则说明有别的程序动了清单
- `list` / `status` / `manage policy` 用免验签读取：用户恰恰需要它们
  在被改动的清单上「看看改了什么」
- 写路径续签规则：有效签名自动续签（向导 / 迁移）；失效或缺失签名的
  文件写完仍不签名（防一次普通写入洗白篡改）；对已签名文件的写入
  必须持钥，无钥写入直接拒绝
- `manage reseal`：手编后的合法化出口，签名密钥随密码库解锁；升级前
  遗留的无签名清单会在第一次强制命令处得到明确报错，reseal 一次即可

## vault 的 key:<host> 命名空间（#37 / #3 基线）

私钥条目放在独立命名空间：`key:<主机名>`。与密码条目隔离是为了
「按主机名查密码」的调用方（`vault.get(name)` / `names()`）不会误把私钥
材料当密码取走：

- `Vault.names()` 只返回密码条目（过滤 `key:` 前缀）
- `Vault.key_names()` 只返回私钥条目
- 条目本身照常 get / set / delete；使用侧已随 P2 密钥认证启用：
  私钥**只以密文存在于 vault**，运行时从内存加载
  （paramiko `from_private_key(StringIO(pem))`），进程退出即消失。
  明文私钥落盘 = 禁止（设计宪法），lib.sshkeys 的任何函数都不写密钥文件
- 管理命令：`manage keygen <主机> [--force]`（生成 / 轮换 Ed25519）、
  `manage keyimport <主机> [文件]`（导入并归一化）、
  `manage keyshow <主机>`（只显示公钥行与指纹）
- 连接编排：**密钥优先，密码兜底**。密钥被服务器拒绝时回落到密码，
  审计写 `auth: password` + `fallback: key`，stderr 有人读提示
- 主机配置的 `key_file` 字段**已不参与认证**（#18）：hosts.toml 对 agent
  可写，磁盘路径上的私钥是不经密码库的托管旁路。字段保留作迁移线索：
  `manage keyimport <主机>` 省略文件路径时自动使用它

## SSHHH_DATA_DIR 仅测试模式生效（#18）

`SSHHH_DATA_DIR` 指到别处就能绕过基于路径的本地保护（put / get 的数据
目录约束、指纹库与签名文件的落点）。因此它**只在 `SSHHH_TEST_MODE=1`
同时存在时生效**；只设 `SSHHH_DATA_DIR` 的组合由入口（sshhh.py 与
console_setup.py）在任何数据访问之前明确拒绝（退出码 3），不是无声忽略。
向导进程经父进程 argv 接收的数据目录是内部可信通道，不受此门禁影响。
正常使用两个变量都不应设置。

## harden --check（只读探测，#37）

`sshhh harden <主机> --check` 连接后检查：sshd 是否 OpenSSH（从握手 banner
识别，不在服务器上执行任何命令）、shell 是否可用、`~/.ssh/authorized_keys`
是否可写（或可创建），输出可加固性报告与建议的 restrict 行模板。
**不执行任何改动**——装公钥 / 服务端包装 / 回滚属 #15 完整实现，在观察名单。

退出码：0 = 具备可加固条件；1 = 探测完成但有阻塞项；4 = 连接失败；
3 = 主机不存在；2 = 用法错误。探测命令（`bash -s` + stdin 脚本）与 test
同一纪律：过主机策略。

只留前两个参数是刻意的：整串 `sys.argv` 会把调用方顺手写在命令里的秘密一起
落盘（`run prod --stdin S3cret mysql -pS3cret` 就是原样两条），而 redactor 只认得
主密码和库里已有的值。落盘前仍会再过一遍 redactor，作第二道保险。

同理，标准输入的内容只能来自管道（`--stdin -`）或 `--stdin-file <文件>`，
**不接受 `--stdin <值>`** —— 值会进 argv、进程列表和审计，所以这种写法现在
直接报参数错误（退出码 2），而不是默默放行。审计记录里也不再有 `caller`
字段：它取自定义方随便就能设置的环境变量，只是「有归属」的错觉。
